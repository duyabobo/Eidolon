# Agent 应用系统架构设计

---

**摘要**

随着大型语言模型（LLM）能力的快速提升，以 Agent 为核心的智能应用正从实验阶段走向生产部署。然而，如何在保障安全隔离的前提下实现多租户并发执行、流式响应输出、工具扩展生态接入，以及动态配置热更新，仍是工程实践中的核心挑战。本文以一个真实落地的企业级多租户 Agent 执行平台为研究对象，系统阐述其分层微服务架构设计，重点分析沙盒双重隔离机制、SSE 流式输出链路、MCP 聚合代理设计、Sticky Session 集群路由优化，以及 LLM 配置热更新方案。在此基础上，本文从安全性、系统解耦性和可扩展性三个维度对架构优势进行系统归纳：安全层面采用纵深防御策略，通过轻量级沙盒双重隔离与网络白名单实现最小攻击面；解耦层面通过消息驱动异步化和标准协议抽象，确保各组件可独立演进；扩展层面所有核心服务均为无状态设计，工具生态通过 MCP 标准协议开放接入。该平台在单节点与集群两种部署模式下均具备良好的生产可用性，可为同类 Agent 应用系统的架构设计提供参考。

**关键词**：大语言模型；Agent 系统；沙盒隔离；微服务架构；MCP 协议；流式输出

---

## 一、引言

大型语言模型（LLM）的突破性进展催生了 Agent 应用的蓬勃发展。不同于传统的问答系统，Agent 能够自主规划任务、调用外部工具、迭代执行多步骤操作，显著拓展了 AI 系统的能力边界。然而，将 Agent 从单用户演示推向多租户生产部署，需要解决一系列工程挑战：

1. **安全隔离**：Agent 在执行任务时可能操作文件系统、运行 Shell 命令，多租户场景下必须严格隔离每个用户的执行环境，防止越权访问和数据泄露。
2. **流式响应**：LLM 的逐 token 输出模式决定了端到端链路必须支持流式传输，否则用户体验大打折扣。
3. **工具扩展**：Agent 的能力边界依赖于可调用的工具生态，系统需要支持运行时动态扩展工具，而非每次重启服务。
4. **弹性扩容**：不同用户的 Agent 任务并发量差异显著，系统需要支持无状态横向扩展。
5. **配置管理**：LLM Provider 的 API Key、Base URL、模型选择等配置需要支持运行时热更新，不能因参数调整而中断服务。

本文以一个企业级多租户 Agent 执行平台为具体研究案例，该平台支持多租户会话管理、轻量级沙盒隔离、SSE 流式输出、MCP 工具扩展和 Skill 渐进式披露等功能。通过对该平台架构的系统性分析，本文旨在总结可复用的设计模式，为 Agent 应用系统的架构设计提供参考。

## 二、相关工作与现状分析

### 2.1 Agent 框架现状与局限

当前主流 Agent 框架可分为两类：

**编排框架**（LangGraph、AutoGen、CrewAI、LlamaIndex Agents）：聚焦于 Agent 内部的规划、工具调用和多 Agent 协作逻辑。这类框架默认运行于受信任的单用户环境，将安全隔离和多租户基础设施问题完全留给上层应用处理。以工具执行节点为例，多数框架直接在宿主进程内调用工具函数，没有进程或文件系统隔离；部分框架虽然支持容器化执行，但容器启动开销（通常 1-3 秒）对于高频会话创建场景代价较高，且缺乏网络白名单机制。

**云服务平台**（OpenAI Assistants API、Anthropic Claude API、Google Gemini API）：提供托管的 Agent 执行环境，用户无需关心基础设施，但代价是黑盒运行——无法自定义执行环境、无法接入私有工具服务、数据主权受限，不适合企业私有化部署场景。

**现有方案的核心局限**：

| 维度 | 编排框架 | 云服务平台 | 本平台 |
|------|---------|----------|------|
| 多租户安全隔离 | 无（共享进程） | 黑盒（未知实现） | bwrap 双重隔离 |
| 私有化部署 | 支持 | 不支持 | 支持 |
| 工具扩展方式 | 代码注册（需重部署） | 有限 API | MCP 标准协议（零停机） |
| 流式 I/O 链路 | 框架内部处理 | SSE（有限控制） | Redis Stream + SSE 全链路 |
| LLM Provider 切换 | 代码改动 | 不支持 | 热更新（零停机） |
| 配置管理界面 | 无 | 有限 Dashboard | 独立 Admin 服务 |

### 2.2 Agent 安全威胁研究

随着 Agent 能力的增强，其安全威胁也在持续演进。学术界和安全社区已识别出多类针对 Agent 的攻击模式：

**Prompt 注入攻击（Prompt Injection）**：攻击者通过构造恶意输入诱导 Agent 执行超出授权范围的操作。Perez & Ribeiro（2022）首次系统性描述了该攻击类别，将其分为直接注入（用户输入包含恶意指令）和间接注入（Agent 读取的外部内容包含恶意指令）两类。Riley et al.（2023）进一步在代码执行 Agent 场景中验证了间接注入的危害性：Agent 读取恶意文件后可能执行任意系统命令。

**越权文件访问**：代码执行类 Agent 若路径校验不严格，可能通过 `../../` 路径穿越访问沙盒外的敏感文件（如 `/etc/passwd`、其他用户数据目录）。

**凭据窃取**：Agent 若能访问环境变量或配置文件，可能将数据库连接串、API Key 等敏感信息外泄。OWASP LLM Top 10（2023）将"敏感信息泄露"（LLM06）和"过度代理权限"（LLM08）列为 LLM 应用的高危风险。

**网络渗出（Data Exfiltration）**：Agent 若拥有网络访问权限，可能将窃取的数据通过 HTTP 请求发送到外部服务器。

上述攻击在现有 Agent 框架中大多缺乏系统性防御，而本平台的沙盒隔离机制在架构层面提供了结构性防护。后续章节将通过具体实验验证各类攻击在本平台中的实际防御效果。

### 2.3 沙盒隔离技术对比

| 技术 | 隔离强度 | 启动开销 | Root 权限需求 | 网络控制粒度 |
|------|---------|---------|-------------|------------|
| Docker 容器 | 高 | 较高（~1-3s） | 需要 Docker daemon | iptables 规则 |
| gVisor (runsc) | 极高（系统调用拦截） | 高 | 需要特权 | 网络策略 |
| **轻量级用户态沙盒（bwrap）** | 中高 | **极低（~50ms）** | **无需 root** | Unix socket 白名单 |
| seccomp-only | 低（仅系统调用过滤） | 极低 | 无需 root | 无 |
| chroot | 低（仅文件系统） | 极低 | 需要 root | 无 |

轻量级用户态沙盒（bwrap）在启动延迟和无 root 权限这两个关键维度上优于其他方案，非常适合高频会话创建场景。其不足是隔离强度低于 gVisor，但结合网络白名单机制后，在 Agent 执行场景中已能满足生产安全要求。

### 2.4 MCP 协议生态现状

Model Context Protocol 由 Anthropic 于 2024 年 11 月发布，迅速获得 OpenAI、Google、Microsoft 等主流厂商支持，成为 Agent 工具集成的事实标准。截至 2025 年，MCP 生态已涵盖数据库访问（PostgreSQL、SQLite）、代码执行（Python REPL）、文件系统、Web 搜索、API 调用等数十类工具服务器，且社区工具数量仍在快速增长。

MCP 的核心价值在于将工具集成从"代码层集成"（需要修改 Agent 代码并重新部署）升级为"配置层集成"（只需注册服务地址），极大降低了工具扩展门槛，是本平台可扩展性设计的基础协议选择依据。

### 2.5 SSE 与 WebSocket 的流式传输对比

| 特性 | SSE | WebSocket |
|------|-----|---------|
| 方向性 | 服务端→客户端（单向） | 双向 |
| 断线重连 | **原生支持**（Last-Event-ID） | 需应用层实现 |
| 反向代理兼容性 | 好（标准 HTTP） | 一般（需 Upgrade 支持） |
| 协议复杂度 | 低 | 较高 |
| LLM token 流场景适配 | **完全匹配** | 可用但过度设计 |

对于 LLM token 流式输出这一典型单向推送场景，SSE 是更简洁、更运维友好的选择。

## 三、系统总体架构

### 3.1 架构分层

本平台采用清晰的三层微服务架构，各层职责分离，依赖关系单向流动：

```
┌─────────────────────────────────────────────┐
│                  接口层                       │
│       会话网关（Gateway）  配置中心（Admin）   │
└──────────────────┬──────────────────────────┘
                   │  消息队列（Pub/Sub）
┌──────────────────▼──────────────────────────┐
│                  执行层                       │
│   Agent 执行引擎    LLM 代理    MCP 代理      │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────▼──────────────────────────┐
│                 持久化层                      │
│       消息流（Redis）  文档 DB（MongoDB）  NFS │
└─────────────────────────────────────────────┘
```

**接口层**负责对外暴露 HTTP API，处理用户请求、会话生命周期管理和配置管理，不直接执行 Agent 逻辑。

**执行层**负责 Agent 任务的实际执行，包括沙盒创建、LLM 调用代理和 MCP 工具代理，通过消息队列与接口层解耦。

**持久化层**提供状态存储、事件流传输和文件共享能力，是多实例横向扩展的共享基础设施。

### 3.2 服务清单

| 服务角色 | 技术栈 | 核心职责 |
|---------|--------|----------|
| 前端界面 | React + Vite + Tailwind | 对话界面与配置管理页 |
| 会话网关（Gateway） | Python FastAPI | 会话 CRUD、SSE 流式输出 |
| 配置中心（Admin） | Python FastAPI | LLM / MCP / Skill 配置管理 |
| LLM 代理（LLM-Proxy） | Python FastAPI | LLM 请求代理，配置热更新 |
| MCP 代理（MCP-Proxy） | Python FastAPI | MCP 聚合代理，工具路由 |
| Agent 执行引擎（Runtime） | Node.js | Agent 任务执行，沙盒隔离 |

## 四、核心组件详细设计

### 4.1 Gateway：会话网关

Gateway 是平台对外的核心接口，基于 FastAPI 实现。其核心职责包括：

**会话生命周期管理**：提供创建会话、发送消息、关闭会话和查询历史四类 RESTful 接口，会话状态持久化在文档数据库中。

**任务派发**：会话创建后，Gateway 通过消息队列将任务异步派发到执行层，由 Agent 执行引擎消费执行。接口层与执行层通过消息中间件解耦，Gateway 无需等待 Agent 执行完成即可返回响应。

**SSE 流式输出**：Gateway 提供两类 SSE 接口：
- **全量历史流**：先回放数据库中的历史事件快照，再持续订阅消息流的增量输出，支持断线重连。
- **按轮次订阅流**：订阅单轮对话的输出，适合轻量级客户端场景。

**幂等性设计**：创建会话时先查询是否存在相同请求的进行中会话，避免重复创建，防止网络重试导致的任务重复执行。

### 4.2 Agent 执行引擎（Runtime）

执行引擎是平台的执行核心，纯消费者角色，不对外暴露 HTTP 接口，全部通过消息队列与接口层通信。

**任务调度流程**如下：

```
消息队列接收任务
  → 记录会话路由信息（Sticky Session 优化）
  → 更新数据库会话状态为 RUNNING
  → 为本次会话创建独立沙盒（工作目录 / 家目录 / 临时目录）
  → 向沙盒注入代理配置（LLM 端点 / MCP 端点）
  → 启动沙盒，以 RPC 模式运行 Agent 进程
  → 解析 Agent 输出流（token / 工具调用 / 工具结果 / done）
  → 逐条写入消息流，供 Gateway 实时推送给客户端
  → 任务完成后销毁沙盒，更新数据库会话状态为 COMPLETED
```

**沙盒生命周期**：每个会话对应一个独立沙盒实例，任务完成后立即销毁，无跨任务状态残留。

**异常恢复**：执行引擎启动时扫描数据库中异常中断的会话，将其置为失败状态，防止因服务重启导致会话状态永久停滞。

### 4.3 沙盒安全架构

沙盒安全是多租户 Agent 平台的核心设计关注点，本平台采用双重隔离策略：

**第一层：文件系统与进程隔离**

基于 Linux 用户命名空间（User Namespace）和挂载命名空间（Mount Namespace），以非 root 权限为每个会话构建独立的文件系统视图：

| 目录类型 | 挂载方式 | 安全作用 |
|---------|---------|---------|
| 系统根目录 | 只读绑定 | 提供系统工具，防止系统文件被篡改 |
| 沙盒数据根目录 | 内存临时文件系统（tmpfs）覆盖 | 对沙盒内隐藏其他会话的持久化数据 |
| 会话工作目录 | 读写绑定 | Agent 可操作的唯一持久化区域 |
| 网络代理 socket 目录 | 只读绑定 | 只允许连接，禁止创建或替换 socket 文件 |

同时通过 PID 命名空间隔离确保沙盒内进程无法感知或操控宿主机进程。

**第二层：网络白名单机制**

网络命名空间隔离切断沙盒内所有外部网络访问。唯一网络出口通过 Unix socket 桥实现——沙盒外的执行引擎预先创建两个 Unix socket 监听文件，分别代理 LLM 请求和 MCP 工具请求，以只读方式挂载进沙盒。沙盒内的 Agent 进程只能向这两个预定端点发起连接，无法创建、删除或替换 socket 文件。

```
沙盒内 Agent 可访问的全部网络资源：
  ┌─ 内部 LLM 端点（loopback → Unix socket → LLM 代理服务）
  └─ 内部 MCP 端点（loopback → Unix socket → MCP 代理服务）

沙盒内 Agent 无法访问：
  ✗ 数据库（无凭据，无网络路由）
  ✗ 互联网（网络命名空间完全隔离）
  ✗ 其他租户的会话数据（tmpfs 内存覆盖隔离）
  ✗ MCP Server 直连（必须经由 MCP 代理）
```

### 4.4 LLM 代理（LLM-Proxy）：LLM 请求代理与热更新

LLM 代理是沙盒内 Agent 访问 LLM 的唯一通道，实现 OpenAI 兼容 API 的透明代理，对 Agent 进程屏蔽真实的 LLM Provider 信息。

**配置热更新**采用内存缓存 + 写穿策略：

```
启动时：从数据库加载配置到内存（一次性 DB 读取）
运行时：每次 LLM 请求 → 直接读内存（零 DB IO）
更新时：管理员修改配置 → 同时写数据库 + 更新内存 → 下一请求立即生效
```

优先级链：数据库配置 > 服务启动时加载的配置 > 环境变量默认值。

这一设计避免了每次 LLM 请求都查询数据库，同时实现了无需重启服务的配置更新，适合频繁调试 LLM Provider 参数的场景。

### 4.5 MCP 代理（MCP-Proxy）：工具聚合代理

MCP 代理基于 MCP 2025-03-26 Streamable HTTP 规范实现，将分散部署的多个 MCP Server 聚合为单一端点。

**懒刷新策略**解决了工具列表动态更新问题：

```
每次 MCP 请求到来时：
  检查距上次刷新是否超过配置的刷新间隔（默认 60s）
    ├── 超过：重新连接所有后端，拉取最新工具列表
    └── 未超过：直接使用内存缓存
```

此策略兼顾了实时性（管理员修改配置后最多 60s 生效）和性能（高频请求不触发数据库查询）。

**工具路由**：MCP 代理维护工具名到后端 Server 的映射表。收到工具调用请求时，根据工具名查找对应后端并转发，对 Agent 进程透明。

### 4.6 配置中心（Admin）：配置管理服务

配置中心承担平台的配置管理职责，与会话网关完全分离，避免管理面操作影响数据面稳定性。提供三类配置管理：

- **LLM 配置**：Provider 的接口地址、密钥、模型选择、超时等参数，写入数据库后由 LLM 代理热加载。
- **MCP Server 配置**：后端 MCP Server 的地址列表，写入数据库后由 MCP 代理懒刷新生效。
- **Skill 管理**：Skill 元数据写数据库，Skill 内容文件写 NFS 共享存储，Agent 执行时通过文件系统只读挂载访问。

## 五、关键技术方案

### 5.1 基于消息流的端到端流式传输链路

端到端流式输出链路如下：

```
Agent 进程（沙盒内）
  → 结构化流式输出（token / 工具调用 / 工具结果 / done 等事件类型）
  → 执行引擎解析并写入消息流（Redis Stream）
  → 会话网关订阅消息流
  → SSE 推送给浏览器前端
  → 前端实时渲染
```

消息流 ID 具有单调递增性，天然支持断线重连（客户端传入上次接收到的消息 ID，服务端从该位置续传）。消息流设置过期时间，避免长期积累占用存储。

历史会话事件通过文档数据库持久化，重新连接时先推送完整历史快照，再订阅实时增量，实现无缝的会话历史恢复。

### 5.2 Sticky Session 集群路由

多实例部署时，同一用户的连续请求路由到同一执行引擎实例可减少跨节点共享存储 I/O，提升沙盒热启动速度：

```
用户发起任务
  → 网关发布任务到公共队列
  → 首次认领：任意执行引擎实例消费，记录用户→实例绑定关系（含 TTL）
  → 后续任务：优先发布到已绑定实例的私有队列
  → 绑定实例优先消费
```

注意：Sticky Session 是性能优化而非安全保证，数据安全由共享存储（NFS）保证，实例故障时其他实例可接管任务。

### 5.3 会话状态机

会话状态流转如下：

```
PENDING → RUNNING → COMPLETED
                  → FAILED
RUNNING → IDLE（沙盒因超时回收）
IDLE    → RUNNING（用户发送新消息，自动重建沙盒）
```

IDLE 状态是本平台的重要设计：长时间无交互的会话沙盒被回收以节省资源，但会话历史在数据库中保留。用户再次发送消息时，系统自动通过"重建沙盒"路径拉起新沙盒，而非"追加消息"路径，对用户透明，无需感知沙盒状态。

## 六、部署架构

### 6.1 单节点部署

通过容器编排工具一键启动所有服务，适合开发调试和小规模使用。平台提供部署脚本，首次运行自动初始化配置文件，无需手动配置各服务间的网络地址。

### 6.2 集群部署

生产集群模式通过覆盖配置实现，核心变化是将本地卷替换为 NFS 共享存储，其余服务配置保持不变。多个执行引擎实例挂载同一 NFS 卷，共享会话工作目录，支持实例故障转移。

接口层和代理层服务均为无状态设计，可独立水平扩展：

| 服务角色 | 扩展方式 | 共享状态载体 |
|---------|---------|------------|
| 会话网关 | 水平扩展（无状态） | 文档 DB + 消息队列 |
| 配置中心 | 水平扩展（无状态） | 文档 DB |
| LLM 代理 | 水平扩展（各实例独立加载配置） | 文档 DB |
| MCP 代理 | 水平扩展（各实例独立缓存工具列表） | 文档 DB |
| Agent 执行引擎 | 水平扩展（Sticky Session 路由优化） | NFS + 消息队列 + 文档 DB |

扩容操作无需修改代码或重启已运行实例，只需调整容器副本数量，新实例自动加入任务消费组。

## 七、设计讨论

### 7.1 职责边界清晰化的价值

本平台严格遵循"单一职责"原则，每个服务有明确的职责边界，并显式声明"不负责"的范畴。例如，执行引擎明确不负责：对外暴露 HTTP 接口、用户认证、LLM 直连、MCP 直连。

这种设计带来了几个优势：(1) 各服务可独立迭代和部署；(2) 故障域隔离，单个服务异常不会雪崩扩散；(3) 安全策略集中实施，沙盒内的 Agent 进程即使被攻破，也无法直接访问数据库凭据或其他用户数据。

### 7.2 接口层与执行层的异步解耦

会话网关通过消息队列将任务派发给执行引擎，而非直接 RPC 调用。这一异步解耦带来了几个好处：(1) 网关响应速度不受 Agent 执行时间影响；(2) 执行引擎可以在不影响接口可用性的情况下重启升级；(3) 天然支持多实例消费，实现执行层的水平扩展。

代价是引入了最终一致性：网关在派发任务后即返回 PENDING 状态，客户端需通过 SSE 长连接获取实际执行结果，增加了客户端实现的复杂度。

### 7.3 安全性与功能性的平衡

沙盒内的 Agent 进程被完全网络隔离，唯一出口是受控的 Unix socket 桥。这一设计在提供强安全保障的同时，也限制了 Agent 的能力边界：Agent 无法自主访问互联网，所有外部资源访问必须经过 MCP 工具代理。这是一个有意的安全取舍，适合企业内部部署场景；如需开放互联网访问，可以通过扩展网络代理白名单来实现精细化的网络访问控制。

### 7.4 Skill 渐进式披露

Skill（技能）以结构化文本文件的形式存储在共享存储中，在沙盒启动时以只读方式挂载。用户可以选择性激活特定 Skill，实现 Agent 能力的渐进式披露，而非一次性暴露所有工具和能力，有助于控制 LLM 的 context 长度和降低幻觉风险。

## 八、架构优势分析

本章从安全性、系统解耦性、可扩展性三个维度，系统归纳本平台架构设计的核心优势，并与业界常见方案进行对比分析。

### 8.1 安全性优势

Agent 在执行任务时具有较强的系统访问能力（文件读写、Shell 执行、网络请求），在多租户场景下，单点安全漏洞可能引发严重的数据泄露或越权访问。本平台在安全设计上采用"纵深防御"策略，构建了多道相互独立的防护层，任意一层被突破均不会导致全局失守。

**（1）沙盒双重隔离：最小攻击面**

绝大多数 Agent 平台将 Agent 进程直接运行于宿主机或容器中，依赖操作系统权限模型进行隔离。本平台则以 bwrap 为基础，为每个 session 创建独立的命名空间沙盒，实现文件系统、网络、进程三个维度的完全隔离：

- **文件系统隔离**：根文件系统以只读方式挂载，会话工作目录独立绑定，内存文件系统（tmpfs）覆盖对沙盒隐藏其他会话的持久化目录。即使 Agent 被恶意 prompt 诱导执行危险命令，也无法访问宿主机敏感数据或其他租户文件。
- **网络隔离**：网络命名空间隔离切断沙盒内所有网络访问，Agent 无法自主发起任何外部请求，彻底消除数据外泄的网络通道。
- **进程隔离**：PID 命名空间独立，沙盒内进程无法感知或干扰宿主机进程。

**（2）网络白名单：最小权限原则**

网络隔离本身会使 Agent 失去 LLM 和工具调用能力，本平台通过 Unix socket 桥解决了这一矛盾：在沙盒内只开放两个预定的内部端口（分别代理 LLM 请求和 MCP 请求），映射到宿主机侧的 Unix socket。socket 文件由宿主进程创建并以**只读**方式挂载进沙盒，Agent 只能 connect（连接）而无法 create/replace（创建或替换），彻底防止 socket 劫持攻击。

```
沙盒内 Agent 可访问的全部网络资源：
  ┌─ 内部 LLM 端点（loopback → Unix socket → LLM 代理服务）
  └─ 内部 MCP 端点（loopback → Unix socket → MCP 代理服务）

沙盒内 Agent 无法访问：
  ✗ 数据库（无凭据，无网络路由）
  ✗ 互联网（网络命名空间完全隔离）
  ✗ 其他租户的服务（无路由）
  ✗ MCP Server 直连（必须经由 MCP 代理）
```

**（3）凭据隔离：零敏感信息下沉**

数据库连接串、LLM API Key、MCP Server 地址等敏感配置全部存储在沙盒外的服务中（数据库、LLM 代理内存），沙盒内的 Agent 进程只持有平台内部颁发的临时访问凭证。即使 Agent 进程被完全攻破，攻击者也无法获取真实的外部凭据，安全边界清晰。

**（4）管控面与数据面分离**

配置中心与会话网关物理分离，管理配置的写入路径与用户请求的执行路径完全隔离。管控面的误操作或攻击不会直接影响数据面的服务稳定性，反之亦然。

---

### 8.2 系统解耦性优势

解耦是系统长期演进和稳定运行的基础。本平台在多个层次上实施了解耦设计，确保各组件可独立变更、独立部署、独立扩展。

**（1）接口层与执行层：消息驱动异步解耦**

会话网关与执行引擎之间不存在直接的 RPC 调用，而是通过消息队列进行单向消息传递。这一设计带来了以下核心优势：

| 场景 | 紧耦合 RPC 方案 | 本平台消息驱动方案 |
|------|--------------|----------------|
| 执行引擎重启升级 | 网关调用失败，影响用户请求 | 网关继续发布任务，执行引擎重启后自动消费积压消息 |
| 执行引擎横向扩容 | 需要网关感知新实例地址 | 新实例订阅同一频道，自动加入消费组，网关无感知 |
| 执行超时 | 需要网关维护超时计时器 | 执行引擎自行管理，网关只关心流结束信号 |
| 峰值流量 | 请求积压导致网关响应变慢 | 消息队列天然削峰，网关响应始终快速 |

**（2）管控面与数据面：职责边界显式化**

本平台每个服务均显式声明"不负责"的范畴，形成清晰的职责矩阵：

| 职责 | 负责方 | 不负责方 |
|------|--------|---------|
| 用户认证 / 会话创建 | 会话网关 | 执行引擎、MCP 代理、LLM 代理 |
| LLM 配置写入 | 配置中心 | LLM 代理（只读配置，不写） |
| MCP 配置写入 | 配置中心 | MCP 代理（只读配置，不写） |
| 工具逻辑执行 | MCP Server | MCP 代理（纯转发） |
| Agent 任务执行 | 执行引擎 | 会话网关（只派发，不执行） |

这种显式边界避免了服务职责蔓延（feature creep），使得单个服务的变更影响面可预测，代码库复杂度保持线性增长而非指数膨胀。

**（3）LLM 与工具调用的标准化解耦**

通过 LLM-Proxy（OpenAI 兼容接口）和 MCP-Proxy（MCP 标准协议），Agent 执行引擎与具体的 LLM Provider 和工具实现完全解耦：

- 切换 LLM Provider（如从 OpenAI 切换到 DeepSeek）只需在配置中心修改接口地址、密钥和模型名，无需改动执行引擎或沙盒代码。
- 新增 MCP 工具只需在配置中心注册新的 MCP Server 地址，60 秒内自动对所有 Agent 生效，不需要重启任何服务。

**（4）持久化层的统一共享**

消息队列（Redis）和文档数据库（MongoDB）作为共享中间件，承载了服务间的状态传递，而非通过服务间直接调用传递状态。这使得任意服务实例都是无差别的（除执行引擎的 Sticky Session 优化外），实例之间没有隐式依赖，可随时替换或重建。

---

### 8.3 可扩展性优势

可扩展性包含两个维度：**水平扩容**（增加实例应对并发）和**功能扩展**（增加新能力不破坏已有结构）。

**（1）无状态服务的水平扩容**

接口层和代理层的服务均为无状态设计，所有运行时状态外置于 Redis / MongoDB / NFS，因此可以无限水平扩展：

```
并发用户增加    → 增加会话网关实例数
工具调用量增加  → 增加 MCP 代理实例数
LLM 请求量增加  → 增加 LLM 代理实例数
```

扩容操作无需修改任何代码，也不需要停机，只需调整容器编排的副本数量。

**（2）执行引擎的弹性扩容**

执行引擎是有状态的（会话工作目录存于共享存储），但通过以下两个设计使其具备弹性扩容能力：

- **共享存储**：所有实例挂载同一 NFS 卷，任意实例可访问任意 session 的工作目录，故障实例的 session 可由其他实例接管。
- **Sticky Session**：在共享存储保证数据可用性的前提下，通过 Redis 记录用户与实例的绑定关系，优先将同一用户的请求路由到同一实例，减少跨节点 NFS I/O，实现性能与扩展性的平衡。

生产集群支持动态伸缩，新实例启动后立即开始消费任务队列，无需注册或服务发现过程。

**（3）工具生态的无限扩展**

本平台通过 MCP 标准协议接入外部工具，工具扩展无需修改平台任何代码：

```
新增工具能力：
  1. 部署新的 MCP Server（任意语言、任意位置）
  2. 在配置中心注册 MCP Server 地址
  3. 约 60s 内 MCP 代理自动发现新工具
  4. Agent 即可调用新工具
```

这一扩展路径完全在平台外部完成，工具开发者不需要了解平台内部实现，平台运营者不需要重启任何服务，形成了开放的工具生态接入机制。

**（4）Skill 能力的渐进式扩展**

Skill 系统提供了另一个维度的扩展能力。通过在配置中心创建 Skill 文件并在会话创建时选择性挂载，可以在不修改 Agent 核心逻辑的情况下，为不同租户、不同场景定制 Agent 的能力集合。Skill 文件以共享存储（NFS）为载体，支持热更新，新 Skill 对下一个会话立即生效。

**（5）部署模式的平滑升级**

平台支持从单节点开发模式到生产集群模式的平滑过渡，无需改动代码，只需替换容器编排配置文件。这一设计降低了项目初期的部署门槛，同时保留了向生产规模演进的路径：

```
开发阶段：单节点模式（本地存储卷，单实例）
    ↓ 无代码改动，仅替换容器编排配置
生产阶段：集群模式（NFS 共享存储卷，多实例）
```

## 九、结论

本文以一个企业级多租户 Agent 执行平台为案例，系统分析了 Agent 应用系统的架构设计。该平台的核心设计理念可总结为以下几点：

1. **分层微服务，职责单一**：接口层、执行层、持久化层严格分离，每个服务有明确的职责边界，复杂性局部化。
2. **异步解耦，消息驱动**：会话网关与执行引擎通过消息队列解耦，接口层与执行层可独立扩展，互不阻塞。
3. **纵深防御，沙盒隔离**：轻量级沙盒文件系统隔离 + Unix socket 网络白名单构成双重隔离，在保障安全的同时最小化了隔离开销。
4. **热更新，零停机**：LLM 配置内存缓存 + 写穿策略、MCP 工具懒刷新策略，实现了配置动态更新，无需重启服务。
5. **流式 I/O 全链路**：从 Agent 的结构化输出，经消息流（Redis Stream），到 SSE 推送，形成端到端的流式响应链路，支持断线重连。

本文第八章从安全性、解耦性、可扩展性三个维度对上述设计进行了系统归纳。**安全性**方面，沙盒双重隔离 + 网络白名单 + 凭据零下沉构成纵深防御体系，即使 Agent 进程被攻破也无法穿透到宿主机或其他租户；**解耦性**方面，消息驱动的异步架构、显式职责边界、OpenAI/MCP 标准协议抽象，使各组件可独立迭代、独立部署，故障域相互隔离；**可扩展性**方面，无状态服务水平扩容、共享存储支撑执行引擎弹性伸缩、MCP 标准协议开放工具生态，使平台能够从单节点开发环境平滑演进至生产集群，无需任何代码改动。

随着 Agent 应用向生产级演进，可观测性、细粒度访问控制、多模态工具扩展、Agent 任务编排将成为架构演进的持续挑战。本文总结的设计模式可为类似系统的架构设计提供参考。
